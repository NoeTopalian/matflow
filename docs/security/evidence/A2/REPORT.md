## Fixes and regression tests
SF-44 (auth.ts, proxy.ts, app/api/auth/[...nextauth]/route.ts, lib/session-revocation.ts): "revoked" → jwt() returns null and the cookie is cleared, as before. "unknown" → jwt() keeps the token stamped with a revalidateSince claim; session() returns {user: undefined, authUnavailable: true}; exported auth() returns null for any unusable session; proxy.ts answers 503 with Retry-After: 15 and does NOT clear the cookie (APIs get JSON {ok:false, retryable:true}; pages a self-retrying "unavailable" page); /api/auth/session also answers 503 and passes through the reissued (not cleared) cookie. The marker is removed only by a pass whose revocation check and legacy temp-password read both succeed; an Edge pass (no check) keeps refusing. Bound: a token still waiting after 24 hours is ended rather than reissued forever; no cached verdict is ever used. Support sessions: resolver or swap failures still end the session (a half-swapped token is the bigger risk). Tests: sec-a2-proxy-outage-cookie (13), sec-a2-outage-proxy-db (6), sec-a2-outage-handlers-db (6).
SF-35 / SF-59 (new lib/auth-lockout.ts, auth.ts): failures counted against the address string, never the account row; bucket names are HMACs in the existing RateLimitHit table, so existing and non-existing addresses behave identically. Two counters: per address+network (10 failures/hour from one /24 IPv4 or /48 IPv6 blocks that network for that address); per address (10 failures/hour from all networks blocks everyone except a known device of that account = a LoginEvent for that person on that device fingerprint, not disowned, seen in the last 90 days). Known-device lookup runs for every capped address (same timing whether the account exists). Only failures count; a successful sign-in clears that network's counter. One refusal code rate_limited for every throttle and lock; account_locked is gone; a row locked by "Wasn't me?" or an operator answers exactly like a wrong password. Row counter still counts failures for the owner/operator view but never locks. Fail closed: counters unreadable → sign-in refused. Client IP now read in the product's trust order (previously the first x-forwarded-for entry, client-chosen). Removed: the per-address attempt limit (5/15 min from any source — itself a lockout anyone could trigger); kept: the per-IP limit. LOGIN_THROTTLE_ENABLED absent or malformed = ON; the value "false" is ignored on any Vercel deployment and on the production database. Tests: sec-a2-lockout-oracle-db (5), sec-a2-lockout-flags (25).
SF-36 (auth.ts): a Google sign-in must match an explicit link keyed on Google's stable sub and bound to one account, checked after every existing refusal and before the account is loaded into the token. Interim (no link store yet): /login?error=google_link_required; nothing loaded into the token, no login event, club cookie not consumed. Test sec-a2-google-link (6).
SF-37: verify routes (new lib/auth-pending-gate.ts) run the revocation check before anything is spent — revoked: 401 + cookie cleared; unknown: 503, nothing spent; the reissued token drops the marker. disown-login: GET renders only a confirmation page (no-store, Referrer-Policy same-origin, noindex); POST requires same origin and does the disown; conditional-update claim so two concurrent confirmations act once. E2E harness: needs E2E_AUTH_BYPASS=true; refused when VERCEL or VERCEL_ENV is set and wherever isTestingMode() refuses; no request header plays any part. Tests: sec-a2-verify-disown-db (8) + flags unit.
SF-27 residual (app/api/member/totp/recover): conditional claim updateMany({totpEnabled: true}) before the write. Test sec-a2-member-recovery-race-db (4).
