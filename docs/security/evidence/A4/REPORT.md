## 1. R6-N1 / SF-111 — lockout cap under a concurrent burst
lockoutState() reserves the failure slot in both counters BEFORE bcrypt using C3's construction: one transaction takes an advisory lock on the address bucket and runs a single conditional insert that counts both windows and inserts both rows only if the pair counter is under 10 and the address counter is under 10 (or the device is known); one lock covers both counters (every network counter belongs to exactly one address); a refused reservation gives the single rate_limited code; the reservation IS the recorded failure (recordFailure() only reads its count and refuses the sign-in if there is no reservation); a correct password deletes that attempt's address row by id (refund) — done before the expired-temporary-password check, since an expired temporary password is not a guess; the unlocked fast read stays in front so an already-capped address is refused without queueing; the known-device exemption is re-checked if a burst fills the cap between read and reservation; lock namespace equals C3's (pinned). Equal cost holds: every address reserves the same way. Design note: the reservation is an interactive transaction with 10 s wait/timeout; Prisma 7 ignores those limits on the batch form C3 uses — in a batch-form run transactions expired at 5 s and 15 of 40 requests failed closed (batch-form-timeout-evidence.jsonl). Burst test sec-a4-lockout-burst-db (judged = reached a password verdict; DB-error refusals reported separately): HEAD 2 failed / 2 passed each role (40 judged, right password admitted, counter 39); fix with test pool 20: 4/4 each role (10 judged, 30 rate_limited, 0 errors, counter 10); fix with production pool 5 (NODE_ENV=production): 4/4 each role, same. Refund: a success after 5 seeded failures leaves the counter at 5. Known device at the cap: admitted, counter stays 10; its own wrong password counts (11); a stranger gets rate_limited. Unit sec-a4-lockout-reservation 11/12 red on HEAD → 12/12 (ordering lock → reservation → bcrypt for every address, refund, fail-closed, burst-race exemption, lock namespace). Mutants (sha256 restores; mutants-summary.txt): M1 bcrypt before reservation — unit 4 red, DB 4/4 green (equivalent for the cap: the verdict still waits for the atomic reservation); M2 no refund — unit 1 red, DB 2 red (counter 6 and 11); M3 refund on failure — unit 1 red, DB 4/4 red (28 judged, counter 0, right password admitted). sec-a3-failure-path-cost: expected trace changed from count, createMany, count after bcrypt to one reserve-tx:2 before bcrypt; 23/23; existing accounts still match no-account at 0/9/10/11. sec-a3-lockout-oracle-db 2/2 both roles; medians differ from no-account by −68..+46 ms (owner) and −75..+57 ms (restricted) at ~45 ms RTT, within R6's noise floor.

## 2. R6-N2 / SF-112 — pending-tenant cookie leaking derived keys
