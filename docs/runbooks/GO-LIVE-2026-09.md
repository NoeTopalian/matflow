# Go live — the operator checklist

**Written 15 Sep 2026, for the Sean Coates meeting on Friday 18 Sep 12:30.**

Every step has an action *and* a way to know it worked. Do not tick a step
because you did it — tick it because you saw the thing that proves it. That
distinction is the whole reason this file exists: three separate things in this
product have been configured, deployed, and silently doing nothing.

Work top to bottom. Later parts assume earlier ones are verified.

---

## Part 0 — What this checklist can and cannot give you

Finishing this makes the product **configured and verified**. It does not make it
**proven in use**, because nobody has run a club on it for a week. Part 8 lists
what remains open afterwards, honestly, so you can decide what to say to Sean
rather than discovering it in the room.

## Part 1 — Error reporting (Sentry)

Without this, nothing that breaks in front of a customer reaches anyone.

1. Vercel → **matflow** → **Settings** → **Environment Variables**. Confirm
   `NEXT_PUBLIC_SENTRY_DSN` exists, Type = **Config**, Production ticked.
   *(Done 15 Sep.)*
2. Wait for the CSP fix (`*.ingest.de.sentry.io`) to be on `main`. Your project
   is on Sentry's **EU** region and the old policy only allowed the US and
   legacy hosts, so the browser would have blocked every event.
3. Vercel → **Deployments** → newest → **⋯** → **Redeploy**.
   `NEXT_PUBLIC_*` is baked in at build time, so this is required, not optional.

**Verify — do not skip:**
4. Open `https://matflow.studio`, press **F12** → **Console**, reload.
   - A red line mentioning `Content Security Policy` and `sentry.io` ⇒ still blocked.
   - Nothing about CSP ⇒ events are getting through.
5. Sentry → your `matflow` project → **Issues**. Trigger a real error if you can
   (visit a URL that 500s) and confirm it appears within a minute.

> **Only tick Part 1 when an event has actually appeared in Sentry.** "The DSN is
> set" is exactly the assumption that made this worth checking.

## Part 2 — Confirm the database migrations applied

Two migrations shipped in commit `3e5ea88`, and a third on 15 Sep. A failed
migration does **not** fail one deploy — it leaves a row in `_prisma_migrations`
with no finish time, and that aborts **every later deploy**, including the one
that would fix it. The recovery command must be run against production from a
laptop, which the repo forbids. So this is worth two minutes now.

1. Vercel → **Deployments** → open the deployment for `3e5ea88`.
2. **Build Logs** → Ctrl+F → `migrate`.
3. Expect `Applied migration` or `No pending migrations to apply`.
4. **If you see any error there, stop and send it to me.** Do not redeploy
   repeatedly — each attempt will fail the same way.

## Part 3 — Stripe, TEST mode first

Do the whole of Part 3 with the **Test mode** toggle ON (top right of the Stripe
dashboard). Nothing here touches real money.

> **Why this matters more than it looks:** production currently holds a live
> restricted key with **no webhook secret**, so `app/api/stripe/webhook` rejects
> every delivery with a 400. No payment, subscription, refund or dispute has ever
> been recorded. The card path has never worked — not once.

1. `dashboard.stripe.com` → confirm **Test mode** is ON.
2. **Connect** → **Get started**. Choose platform / "other businesses take
   payments through you".
3. `dashboard.stripe.com/settings/connect` → **Integration** → copy **Client ID**
   (`ca_…`). Save as `STRIPE_CLIENT_ID (test)`.
4. Same page → **Redirects** → **Add URI** → exactly:
   ```
   https://matflow.studio/api/stripe/connect/callback
   ```
5. `dashboard.stripe.com/webhooks` → **Add endpoint** → URL exactly:
   ```
   https://matflow.studio/api/stripe/webhook
   ```
6. **TICK "Listen to events on Connected accounts".**
   MatFlow uses direct charges to each gym's own account. Without this box,
   platform-only events arrive and **every member payment is missed**. This is
   the single most important click in this document.
7. **Select events** — these 19, no more:
   `checkout.session.completed` · `checkout.session.expired` ·
   `customer.deleted` · `customer.subscription.deleted` ·
   `customer.subscription.updated` · `invoice.payment_failed` ·
   `invoice.payment_succeeded` · `invoice.voided` ·
   `payment_intent.processing` · `payment_intent.succeeded` ·
   `payment_intent.payment_failed` · `mandate.updated` · `charge.refunded` ·
   `payment_method.detached` · `charge.dispute.created` ·
   `charge.dispute.updated` · `charge.dispute.closed` · `account.updated` ·
   `account.application.deauthorized`
8. Save → open the endpoint → **Signing secret** → **Reveal** → copy (`whsec_…`).
9. `dashboard.stripe.com/apikeys` → copy **Publishable key** (`pk_test_…`) and
   reveal + copy **Secret key** (`sk_test_…`).
10. **Send me those four test values.** They go in `.env.test` only — never
    Vercel. I run the card tests against them.

> **Never put a LIVE key in `.env.test`.** The test suite records payments. The
> database guard cannot guard a payment processor.

## Part 4 — Stripe, LIVE mode

Only after Part 3 is verified.

1. Toggle **Test mode OFF**.
2. **Activate the account** if not already: legal name, address, DOB, bank
   account for payouts. Live keys cannot charge until this is complete.
3. Repeat steps 3–9 of Part 3 **in live mode**. Live has its own separate client
   ID, its own webhook endpoint, its own signing secret and its own keys. None
   of the test values carry over.
4. Vercel → **Settings** → **Environment Variables** → Production:

   | Key | Type | Value |
   |---|---|---|
   | `STRIPE_SECRET_KEY` | **Secret** | `sk_live_…` |
   | `STRIPE_WEBHOOK_SECRET` | **Secret** | `whsec_…` (live endpoint) |
   | `STRIPE_CLIENT_ID` | **Secret** | `ca_…` (live) |
   | `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` | **Config** | `pk_live_…` |

   Rule: anything starting `NEXT_PUBLIC_` is Config — the prefix means "send this
   to the browser". Everything else is Secret.
5. **Redeploy.**

**Verify — this is the step that decides it:**
6. Sign in to `matflow.studio` as owner, then open:
   ```
   https://matflow.studio/api/stripe/connect/health
   ```
7. Look for `"ready": true`. If `false`, it lists exactly what is missing in
   `nextSteps` — send me that list.

> **Do not treat Stripe as set up until this endpoint says `ready: true`.** It
> checks the client ID's format, that the secret key actually authenticates
> against Stripe, that the webhook secret is present, and that the redirect URI
> matches. It exists precisely so this is not a matter of opinion.

8. The existing `rk_live_` restricted key: if step 7 reports the platform-account
   call failing, replace it with a standard `sk_live_…`. A restricted key may
   lack Connect scope.

## Part 5 — The ID card, before Thursday

The only part of the demo no test can cover. `BarcodeDetector` is a code path
with no prior art in this repo and camera support varies by handset.

1. MatFlow → **Members** → open any member → print their card
   (or go to `/print/member-cards`).
2. Print on real A4. Cut it out.
3. On **the phone that will be in the room** — not a different one — open
   MatFlow → **Scan Cards**.
4. Allow camera access. Point it at the card.
5. Confirm it registers a check-in.
6. If it fails: tell me the phone model, browser, and what you saw.

> Cards may be printed for testing. **Do not issue cards to real members** until
> this has succeeded once.

## Part 6 — Email deliverability (DMARC)

Missing since mid-August. Matters on the ~200-invite onboarding day.

1. Your DNS provider for `matflow.studio` → add a **TXT** record:
   - **Name/Host**: `_dmarc`
   - **Value**: `v=DMARC1; p=none; rua=mailto:noe@matflow.studio`
2. Save. Propagation is usually minutes.
3. Verify at `mxtoolbox.com/dmarc.aspx` → enter `matflow.studio` → expect the
   record to be found.
4. Also confirm in Vercel that `RESEND_FROM` is an `@matflow.studio` address —
   otherwise every email still sends from the Resend sandbox sender and all the
   DNS work is inert.

## Part 8 — What is still NOT production ready, after all of the above

State this plainly to yourself before Friday. None of it is a reason not to sell;
all of it is a reason not to over-claim.

- **Nobody has run a club on this for a week.** Everything is verified; nothing
  is seasoned. The first real onboarding will surface things no test did.
- **The legacy e2e suite has ~30 failures**, untriaged, red nightly since 9 Sep.
  Separate from the new campaign suite, which is green.
- **Vercel Hobby forbids commercial use** and caps crons at 2 while 3 are
  declared — so one may never run, and the repo's own audit flags
  `class-instances` as the likely casualty, meaning timetables could silently
  stop generating. Upgrading to Pro (~£20/mo) resolves both.
- **Neon free keeps 6 hours of backups**, while `/legal/privacy` promises 7–30
  days. Either upgrade or correct the policy — correcting it is free and is
  currently a false statement to customers.
- **The S3 backup has failed every Sunday since 12 July.** Neon PITR is the only
  backup, with the window above.
- **Nine operator-plane routes are cookie-reachable with no origin check**, and
  the `matflow_admin` cookie is the raw shared secret. Real, open, and larger
  than a single fix.
- **No member roster export exists.** The loudest complaint in the market survey
  is vendors holding data hostage, and the product currently does it.

## If something goes wrong

- **A deploy fails right after a migration**: do not retry. Send me the build log.
- **Stripe health says `ready: false`**: send me its `nextSteps` array verbatim.
- **Sentry shows nothing**: F12 → Console → look for a CSP error naming
  `sentry.io`.
- **Anything returns a `MF-` reference code**: send me the code. It identifies
  the exact error server-side.
