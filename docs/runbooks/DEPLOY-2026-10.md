      lock is bounded by `lock_timeout` — none is set — so a query that's
      mid-flight against `Class` or `Tenant` when the migration starts will
      queue behind it, and everything that arrives after queues behind that
      query. Pick a window with no scheduled classes for any live tenant
      (today: demo clubs only) and push then.

## 2 — Push and watch

- [ ] `git push origin main` (Noe).
- [ ] Vercel auto-deploys on push. Open the deployment → **Build Logs**.
- [ ] Watch for the `maybe-migrate` output. Expected sequence:
      1. `[build] DATABASE_URL set — running \`prisma migrate deploy\`` —
         confirms `VERCEL_ENV=production` and `DATABASE_URL` is set (the
         script exits 0 silently on preview builds without it, and refuses
         to migrate the prod endpoint from a non-production deploy — see
         `scripts/maybe-migrate.mjs`).
      2. One `Applying migration \`<name>\`` line per pending migration, in
         the order listed in §1, each followed by success — no
         `Applied migration` failure text.
      3. `next build` proceeds to compile as normal.
- [ ] **What failure looks like, and what to do:**
      - **A migration fails mid-apply** (the build log shows an error under
        a specific migration name, then the process exits non-zero): the
        deploy is aborted, the old build keeps serving (Vercel does not cut
        traffic to a failed build), but `_prisma_migrations` now has a row
        for that migration with `finished_at IS NULL`. This blocks **every
        later deploy** with Prisma error P3009 until it's resolved. **Do
        not retry by pushing again or hitting Redeploy — it will fail the
        same way.** Noe runs, against production:
        ```
        npx prisma migrate resolve --rolled-back <migration_name>
        ```
        then diagnoses and fixes the migration SQL before re-pushing.
      - **All migrations succeed but `next build` fails** (e.g. a
        TypeScript or lint error surfaces only at build time): the schema
        is already forward, but no new code shipped. The old build keeps
        serving — the brief's own note confirms the old build is compatible
        with the new schema, so this is safe to sit with. Fix forward: fix
        the build error, commit, push again. Do not attempt to revert the
        schema.
      - **Build and migrations both succeed but the deploy doesn't
        promote** (rare — Vercel infra issue): check Vercel's status page,
        retry the deploy from the dashboard once confirmed it's not a code
        issue.

## 5 — Recovery

- [ ] **Preferred: Instant Rollback.** Vercel dashboard → Deployments → the
      last known-good deployment (pre-this-push) → **⋯** → **Promote to
      Production** (this is Vercel's "Instant Rollback" — traffic cuts over
      in ~30s). **The schema stays forward** — rolling back the deployment
      does not undo the 5 migrations, and there is no down-migration to run
      (Prisma doesn't generate one; see `docs/RUNBOOK.md` → Migration
      rollback). Confirm the old build is still compatible with the new
      schema before relying on this (per the brief, it is).
- [ ] **If a migration itself failed and left `_prisma_migrations` with
      `finished_at IS NULL`:** this is not fixed by rolling back the
      deployment. Noe runs, against production:
      ```
      npx prisma migrate resolve --rolled-back <migration_name>
      ```
      then either fixes forward (re-push with a corrected migration) or, if
      the migration partially applied destructive DDL, follows
      `docs/RUNBOOK.md` → Migration rollback → hand-write the inverse SQL.
      **Drilled 30 Sep 2026** (throwaway schema on the test branch, built from
      production's schema at `ac2fcb8`, the candidate's migrations plus a
      forced failure after `locations`): Prisma does **not** wrap a migration
      in a transaction — an unwrapped failing migration left its first
      `ALTER TABLE` behind. Every candidate migration therefore wraps itself
      in `BEGIN; … COMMIT;` (pinned by `tests/unit/migrations-are-atomic.test.ts`);
      with that, the failure left nothing behind, later deploys were refused
      with P3009, `resolve --rolled-back` succeeded, and the forward redeploy
      applied all 86 migrations. Before resolving, still confirm in the Neon
      console that nothing from the failed migration exists (for `locations`:
      `SELECT to_regclass('"Location"')` is NULL).
- [ ] **Data risks of a rollback**, specifically because the schema stays
      forward while the code goes back:
      - **Billing cycle (weekly)**: the old build has no concept of a
        weekly (or fortnightly/four-weekly) billing cycle. Any member whose
        tier was set to one of those cycles by the *new* code, before a
        rollback, will be read and displayed by the *old* code as if it
        were monthly — dates and amounts will be wrong in the UI until the
        new code is back.
      - **Forced password change** (`User.mustChangePassword` from the
        `20260926130000` migration): the old build does not check or
        enforce this flag. Any user flagged to be forced through a password
        change by the new code will, after a rollback, log in normally
        with their existing password — the enforcement silently stops
        until the new code is redeployed.
      - Neither of these corrupts data — the columns and values are still
        there — but both are behavioural regressions to expect and to
        explain if the rollback needs to sit for more than a few hours.

## 6 — After go-live (G1)

Do these only once the deploy above is stable — not in the same push.

- [ ] **`CRON_SECRET`**: before setting this, Noe runs the retention dry-run
      and reads the counts as a human — this is a one-way door the first
      time it runs for real (it purges a year of logs, 90 days of Stripe
      events, and hard-deletes any tenant past its 30-day soft-delete
      grace):
      ```
      GET https://matflow.studio/api/cron/retention?dryRun=1
      Authorization: Bearer <CRON_SECRET candidate value>
      ```
      Read the `results[].details` counts in the JSON response — in
      particular `tenantHardDelete.details.wouldPurge` (names every tenant
      that would be hard-deleted) — before deciding to set `CRON_SECRET` in
      Vercel for real. Once satisfied, set `CRON_SECRET` in Vercel →
      Settings → Environment Variables → Production, then redeploy (or wait
      for the next request — env vars for a cron's own bearer check are
      read at request time, but `lib/env-guards.ts`'s boot-time warn only
      updates on redeploy).
- [ ] **`RESEND_FROM` + DMARC**, per `docs/EMAIL-SETUP-RUNBOOK.md`: confirm
      `RESEND_FROM` is set to a verified `@matflow.studio` (or
      `mail.matflow.studio`) address, not the Resend sandbox sender, and
      that the `_dmarc.matflow.studio` TXT record resolves
      (`mxtoolbox.com/dmarc.aspx`). Until both are true, MatFlow can only
      email `noetopalian@gmail.com` — every other invite/magic-link/alert
