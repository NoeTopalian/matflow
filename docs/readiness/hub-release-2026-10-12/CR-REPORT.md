**SF-135, precisely.** Prisma 7.4.2's transaction-timeout timer fires while one of our statements is still in flight (queued on the per-bucket advisory lock or stalled on the network). The timer can only queue a ROLLBACK behind that statement. When the socket then ends, pg rejects both: the statement's rejection reaches our caller (which refuses the request), and the timer's ROLLBACK rejection has no handler — an **unhandled promise rejection** (L1 REPORT §1). Measured impact (L1 REPORT §2): no admission, no client leak, no lost counter, no misreported security outcome; plain Node and Vitest exit 1, while Next.js 16.3.8 logs `⨯ unhandledRejection` and keeps serving (repro.txt §6). At 704ab57 it fires from the reservation (`auth-lockout.ts:159`, 10 s), the rate limit (`rate-limit.ts:86`) and the sign-in flow's tenant/bypass transactions (`prisma-tenant.ts:54`, 15 s) — L1 cycle 1 measured 14 unhandled rejections across 6 of 12 `sec-a4` runs from the last source. Classification: availability / test false-red; the ledger reassessed it Medium "no security weakening found" (FINDINGS.md:154 (main)).

**SF-136, precisely — which write is lost.** When Prisma's `maxWait` expires while the transaction **start** (pool acquisition or `BEGIN`) is still pending, the caller gets P2028; when the start then completes, `@prisma/adapter-pg` 7.4.2's discard path only releases the client (no `ROLLBACK`), so the client goes back to the pool **inside an open `BEGIN` that nobody owns** (proposals.txt:24-35 (main)). The write that is lost is **not the timed-out transaction's own work** (its callback never ran) — it is **whatever plain, autocommit statement the next borrower of that pooled client issues**: it executes inside the orphan transaction, is visible only to that connection, and is lost when the connection is rolled back or closed (repro.txt:154-159 (main): `clientReturnedInsideTransaction:true`, `plainWriteSeenBeforeClose:1`, `plainWritePersistedAfterClose:0`, both roles). If the next borrower instead runs a transaction, Postgres ignores its nested `BEGIN` and its `COMMIT` commits the orphaned work late, or its `ROLLBACK` discards it. Production has `idle_in_transaction_session_timeout` 300 s (FINDINGS.md:154 (main)), which would end such a session and so discard any orphaned writes.

Reach at 704ab57 (proposals.txt:31-33 (main)): `checkRateLimit`'s batch transaction (2 s Prisma default, below the 10 s pool deadline — so ordinary pool saturation suffices) and the three 10 s openers (racing the equal 10 s pool deadline). Bare-client writes that can be the victim on the sign-in path at 704ab57: the refund `clearPairOnSuccess` (`lib/auth-lockout.ts:262-266`, `prisma.rateLimitHit.deleteMany`) and the rate limiter's prune (`lib/rate-limit.ts:113-116`). Losing the refund **over-counts** (the real person's slot stays spent) — the fail-safe direction. The reservation insert itself is inside its own interactive transaction (`auth-lockout.ts:175-199`) and commits with its own `COMMIT`, so **a failed-login reservation is not lost on this path and the per-address cap does not under-count** through SF-136; L1 measured "no lost counter" on the SF-135 path (REPORT §2) and named no security write lost under SF-136. The general consequence is a **silent loss (or late commit) of an unrelated autocommit write on the same instance under pool pressure**, which is why the ledger rates it Medium. I found no evidence, and L1 states none, of an admission or a cap under-count resulting from it.

**User-visible effect of a login attempt during a burst at 704ab57.**
1. Below the cap, ordinary concurrency: the attempt queues on the per-address advisory lock while holding a pooled connection (SF-118), then gets a verdict.
2. Once 10 failures for the address are recorded in the hour, any network that is not a known device of the account gets `RateLimitedError` (`auth.ts:527-534`), shown as the throttle message (`lib/auth-lockout.ts:76-77`) — by design.

If the reservation cannot be made in time (pool saturated past the 10 s acquisition deadline, P2028, a dropped connection, or the 10 s transaction timeout while queued on the lock), `lockoutState` throws; the outer catch re-throws only the three message-bearing errors (`auth.ts:792-802`) and in production returns `null` (`auth.ts:809`), which the login page renders as **"Incorrect email or password."** (`app/login/page.tsx:83`) — **even when the password was right** (SF-118 wording residual; measured ~13 s wait before the refusal with the lock held, FINDINGS.md:137 at 704ab57). 5. Server side, SF-135 may log an unhandled rejection; the process survives. SF-136 may silently drop or delay an unrelated autocommit write.

## 4. Replacement-address contract at 704ab57

Rules the code enforces on a replacement address (member contact-email `newEmail`; owner login-email `newEmail`; both via `emailField(120)`, `lib/email-normalise.ts:39-41`):
1. A string; trimmed, then validated by zod 4.3.6 `z.string().email()` (`package-lock.json` `node_modules/zod` 4.3.6), then length ≤ 120, then lower-cased (`lib/email-normalise.ts:27-29,:39-41`). Stored lower-case and trimmed.
2. The zod 4.3.6 default email pattern is ASCII-only: `^(?!\.)(?!.*\.\.)([A-Za-z0-9_'+\-\.]*)[A-Za-z0-9_+-]@([A-Za-z0-9][A-Za-z0-9\-]*\.)+[A-Za-z]{2,}$` (read from `node_modules/zod/v4/core/regexes.js:26` in the main checkout, same version as 704ab57's lockfile). So **Unicode local parts and Unicode domains are refused**; a punycode (`xn--`) domain is accepted; `+` and `'` are accepted; no leading dot, no `..`.
3. **Uniqueness is per club across both tables**: `claimLoginIdentity` takes a transaction-scoped advisory lock on (club, canonical address) and finds every `User` and `Member` in that club whose `lower(btrim(email))` equals it (`lib/login-email.ts:149-167,:176-212,:228-242`). The database constraints are per table and on the raw value only: `User @@unique([tenantId, email])` (`prisma/schema.prisma:180`), `Member @@unique([tenantId, email])` (`prisma/schema.prisma:350`), created as `User_tenantId_email_key` / `Member_tenantId_email_key` (`prisma/migrations/20260424205716_init/migration.sql:245,:248`). Cross-table and case-folded uniqueness is therefore an application rule enforced by the lock, not a database constraint. The same address in **another club** is allowed.
4. Member route only: must not be synthesised or an erasure sentinel (`contact-email/route.ts:78-79,:164`), must differ from the current address (`:165`).
5. Owner route only: must differ from the owner's current address (`login-email/route.ts:123-131`).

What the code does NOT check:
- **Plus-aliases and dots are not folded**: `owner+member@x` is a distinct address from `owner@x` and is **allowed** (`lib/login-email.ts:89-90`). The admin-hub FINAL-REPORT step 4 (main) itself plans a `+member` address for the member row; the decision document's step 3 (a separate real mailbox, not an alias) is a human rule the code does not enforce.
- The **owner route does not refuse** the synthesised `@no-login.matflow.local` domain or the erasure sentinel `@deleted.invalid` as a new login (no such check in `login-email/route.ts:72-76,:204-219`); the zod pattern accepts both TLDs. Only the member route refuses them.
- **Deliverability**: no DNS/MX lookup anywhere in `app/` or `lib/` (no `dns` import found); no confirmation mail (delivery is off).
- `Member.unverifiedEmail` is not consulted for collisions (`lib/login-email.ts:189-193` reads `email` only), so an address held only as another record's `unverifiedEmail` is "free".
- Address ownership: nothing ties the replacement to the person; the reason text and the operator's attestation are the only record.

## 7. Build order, partial failure, migration compatibility
