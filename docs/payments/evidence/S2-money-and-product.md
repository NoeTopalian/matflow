- Ad-hoc staff charge: `paymentIntents.create(... off_session, confirm)` with `{ stripeAccount, idempotencyKey }` — app/api/members/[id]/charge/route.ts:165-177.

**Platform fee taken in code: NONE.** A repository-wide search for `application_fee`, `transfer_data`, `on_behalf_of`, `transfers.create`, `transfer_group` and `payouts.` across app/ and lib/ returns no Stripe usage (the only `destination` hits are unrelated redirects, app/api/magic-link/verify/route.ts:329). This matches the owner's model (platform fee by bank transfer, checked manually). Status: IMPLEMENTED (absence confirmed by search); not separately tested.

**Merchant of record / Stripe fees / refunds / disputes:** because charges are direct on the Standard account and no application fee or transfer exists, Stripe processing fees, refunds and dispute losses fall on the club's own balance by construction. (Provider-side confirmation of MoR and fee responsibility is Lane S3's.) Refunds are issued by MatFlow on the connected account (refund route above; owner-only, see §15) or by the club directly in Stripe, in which case only `charge.refunded` reaches MatFlow (app/api/stripe/webhook/route.ts:630-725; it updates an existing Payment only — a refund on a charge MatFlow has no Payment row for is logged and dropped, :649-656).

**Disputes:** `charge.dispute.created|updated|closed` handled at app/api/stripe/webhook/route.ts:910-1111. It upserts a `Dispute` row keyed on `stripeDisputeId` (unique, prisma/schema.prisma:1202-1219), links it to a Payment by charge id then PI id (:924-929), maps lost/charge_refunded to Payment `refunded` and anything else open to `disputed` (:975-1025), voids a funded class pack on loss (:1005-1019), sets Member.paymentStatus `overdue` unless won (:1033-1041), audits (:1048-1063) and emails owners on creation (:1069-1110). Evidence submission is NOT in MatFlow — owners respond in Stripe. Status: IMPLEMENTED; test coverage see §16.

**Payouts:** no payout API calls and no `payout.*` event handling (handled set lib/stripe/handled-events.ts:24-50). `payoutsEnabled` is only cached from `accounts.retrieve` (lib/stripe-account-status.ts:47-54) and never gates anything (`canAcceptCharges` reads chargesEnabled only, :119-123). Payouts are entirely Stripe ↔ club. Status: MISSING by design (no MatFlow role).

**DEFECT (money can route to the PLATFORM account): shop checkout.** app/api/member/checkout/route.ts:220 sets `connectedAccount = tenant.stripeConnected ? tenant.stripeAccountId : undefined` and :294 passes `connectedAccount ? { stripeAccount: connectedAccount } : undefined`. If `stripeAccountId` is set but `stripeConnected` is false, the Checkout Session is created on MatFlow's PLATFORM Stripe account. That exact state is what `account.application.deauthorized` produces: the handler deliberately keeps `stripeAccountId` and sets `stripeConnected: false` (app/api/stripe/webhook/route.ts:1182-1210). The only barrier is the charge gate at :208-218. Right after deauthorisation the cached status is stamped `chargesEnabled:false` (webhook :1200-1207), so the gate blocks; but after 24 h the cache is stale (lib/stripe-account-status.ts:136-146) and is re-read with `accounts.retrieve` on an account the platform no longer has access to. If Stripe answers with an error classified as a permission error, the helper FAILS OPEN with `chargesEnabled:true` (lib/stripe-account-status.ts:68-84) and the member's card is then charged on the platform account. Every other card route refuses when `!stripeConnected` (e.g. app/api/member/class-packs/buy/route.ts:78, app/api/member/subscriptions/start-for-kid/route.ts:96, app/api/stripe/create-subscription/route.ts:55), so this is the one inconsistent path. Platform-account sessions also carry no `event.account`, so their webhooks would 409-retry forever and the Order would never flip to paid (app/api/stripe/webhook/route.ts:144-146). Which error Stripe returns for `accounts.retrieve` on a deauthorised Standard account is UNKNOWN (needs a test-mode run); the inconsistency in code is certain. Owner relevance: with the agreed model MatFlow must never be merchant for a club's sale.

**Secondary routing observations:**
- The refund route and the staff charge route check `stripeAccountId` only, not `stripeConnected` (app/api/payments/[id]/refund/route.ts:113; app/api/members/[id]/charge/route.ts:141). - Order rows are written without `currency` (app/api/member/checkout/route.ts:258-267) so they take the schema default `GBP` (prisma/schema.prisma:1253) while the session charges in the tenant currency (:226). Only matters for a non-GBP club.

## 10. Linking to people

**Customer ↔ Member.** `Member.stripeCustomerId` and `Member.stripeSubscriptionId` (prisma/schema.prisma:267-268). A partial unique index makes a customer id unique per tenant: `Member_tenantId_stripeCustomerId_unique ... WHERE "stripeCustomerId" IS NOT NULL` (prisma/migrations/20260601000002_area8_rls_fk_indexes/migration.sql:59-61). So one Stripe customer can belong to only one MatFlow member in a club. A customer is created lazily, on the connected account, with the member's `email` and `name` (lib/stripe/subscriptions.ts:88-107; app/api/member/class-packs/buy/route.ts:109-126) and written with a compare-and-set so concurrent first purchases converge on one id (`updateMany where stripeCustomerId: null`). The losing request's Stripe customer is left orphaned on the club's account (no delete) — a duplicate-customer source, low impact. No code ever calls `customers.update`: a later change to the member's name or email is never pushed to Stripe (search of all Stripe call sites, §4 list). Status: IMPLEMENTED; not tested at integration level.

**Subscription ↔ membership.** `Member.stripeSubscriptionId` holds ONE subscription; the tier is `Member.membershipTierId`. Starting a subscription writes only the subscription id and preferred method (lib/stripe/subscriptions.ts:191-199) — it does NOT set `membershipTierId` from the chosen price (the member routes look the tier up only to validate, app/api/member/subscriptions/start-for-kid/route.ts:139-153). The migration does write the tier (lib/stripe/migrate-memberships.ts:589, 680).

**Invoice ↔ Payment.** `Payment.stripeInvoiceId` @unique, `stripePaymentIntentId` @unique, `stripeChargeId` indexed (prisma/schema.prisma:1161-1163). Invoice and PaymentIntent legs converge on one row keyed by the resolved PI (app/api/stripe/webhook/route.ts:399-435; resolver lib/stripe/invoice-payment.ts). FIXTURE-TESTED (stripe-webhook-handlers.test.ts:277-367, :1125-1149); test-mode run 24 Sep.

**Webhook member resolution is by customer only.** `findMember(customerId)` = `findFirst where { stripeCustomerId, tenantId }` (app/api/stripe/webhook/route.ts:155-175). Every member-affecting branch (invoice paid/failed, subscription updated, PI succeeded/processing, dispute) attributes by customer, so any charge on that customer — including one MatFlow did not create — is mirrored onto that member (see §17 for the TeamUp consequence).

**Guardian-paid children.** `start-for-kid` creates a SEPARATE Stripe customer for each child, using the child's own Member email — which for a child is a synthesised no-inbox address (app/api/member/subscriptions/start-for-kid/route.ts:180-188, comment :10-18). The parent enters a card for each child's customer through the Payment Element; the file comment says the method "defaults to the parent's saved card", but no code copies or attaches a parent payment method (no `paymentMethods.attach` anywhere in app/ or lib/). So: whose customer = the child's; whose payment method = whatever the parent enters, per child; Stripe-side receipts (if the club enables Stripe receipts) would address the child's synthesised email. MatFlow's own failure email re-routes to the parent (webhook :311-315). Guardianship must be confirmed (`CONFIRMED_GUARDIAN`, :127). Family billing read: app/api/member/family/[id]/billing/route.ts; family portal: app/api/member/family/[id]/billing/portal/route.ts:73-88. Status: IMPLEMENTED; FIXTURE-TESTED (tests/unit/family-authority-routes.test.ts, member-subscribe-duplicate-guard.test.ts:145-175); test-mode run 26 Sep (stripe-family-e2e JSON, result PASS).

**Migration matching (existing customers).** The migration lists every customer on the connected account and matches to members by lower-cased email only (lib/stripe/migrate-memberships.ts:214-262, 515). Duplicate customers on one email are resolved silently: prefer the one with a live subscription, else the newest (:248-261). A child never matches (synthesised email). The cutover manifest refuses to treat an email match as proof of payer: every payer is `verified: false` without an explicit parent link or owner confirmation (lib/stripe/cutover-manifest.ts:16-21; docs/runbooks/CUTOVER-MANIFEST-TEMPLATE.md:14).

**Reconnect to a different account.** After a disconnect (`stripeAccountId: null`, app/api/stripe/disconnect/route.ts:42) or deauthorisation, `Member.stripeCustomerId`/`stripeSubscriptionId` are NOT cleared, so after connecting a different Stripe account the members point at customers that do not exist on it. No code detects this. UNKNOWN impact until a run (calls would 404 at Stripe).

**Email semantics.** `Member.email` is both the login identifier and the Stripe customer email at creation; `Member.unverifiedEmail` is an import-seen contact address that is "never a login" (prisma/schema.prisma:202-204); staff login emails can be provisional identifiers, not verified mailboxes (lib/login-email.ts:1-23). Consequences: (a) the Stripe customer email is whatever the member row held at first purchase and is never updated; (b) migration matching uses `Member.email`, so a member whose MatFlow email differs from the TeamUp/Stripe customer email is `no_customer` (skipped, not mis-linked), and a shared family email links the adult whose row carries it. Ambiguous matches are resolved by the owner through the preview, not by code.
