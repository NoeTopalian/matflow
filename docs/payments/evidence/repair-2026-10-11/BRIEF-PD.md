Design to implement:
1. Two-phase durability in `event-store.ts`: `recordReceived(event)` upserts the row (`status: received`, attempts+1) in its OWN short transaction BEFORE processing; `markProcessed(eventId)` / `markIgnored(eventId, kind)` / `markFailed(eventId, error)` after. Processing itself stays inside one transaction (the handler's), so a crash mid-handler rolls the handler back but the `received` row survives with the error on the next attempt. Duplicate delivery: a row already `processed|ignored_*` returns `alreadyProcessed` without re-running; a row `received|failed` is eligible for re-processing (Stripe retry or replay). Concurrency: two deliveries of one id must not both process — use the row as the lock (conditional update `status = received AND processingToken IS NULL` → set token; or a per-event advisory lock inside the handler transaction, consistent with `lib/rate-limit.ts` style); prove it with a two-connection DB test. Return codes: keep non-2xx for a failed handler so Stripe also retries, but the row now records the failure.
2. Replay (`replay.ts`): operator-only; takes an event id, retrieves the event FRESH from Stripe with `Stripe-Account` (per the docs; never from a stored payload), re-runs the same processing path (expose a `processStripeEvent(event)` function signature in your note for PC to wire; until then, replay calls the current handler through an exported entry point if one exists, otherwise document the gap), marks `replayed`, audits `stripe.event.replayed` with operator id, event id, tenant, outcome. Replay of a `processed` event is refused (idempotent: nothing to do) unless `force` with a reason, and even then the handler's own idempotency (unique Payment keys, mapping rules) must make it a no-op — test that a forced replay of a processed `invoice.payment_succeeded` creates no second Payment row and no second audit/email side effect.
3. Reconciliation (`reconcile.ts`): per connected club (INCLUDING `stripeConnected: false` clubs that still hold an id — report, do not call Stripe for deauthorised ones), (a) list events for the window with `Stripe-Account` and `delivery_success=false` where the API allows, compare with the store, record missing ones as `received` with `attempts: 0` and a `reconcileFoundAt` marker (do not process them automatically; replay is operator-controlled); (b) STATE comparison: for every active `MemberSubscription`/`Member.stripeSubscriptionId`, retrieve the subscription and compare status/current_period_end with the stored mirror; for Payments in the window compare status/amount_refunded with the charge; write a `StripeReconcileRun` summary row (new small model is allowed: runId, startedAt, finishedAt, tenantsChecked, eventsMissing, stateMismatches Json (ids and fields only, no amounts beyond pence, no PII), status). Never writes member or payment state. Schedule: add `/api/cron/stripe-reconcile` to `vercel.json` (daily, off-peak); the route keeps its `CRON_SECRET` bearer check and adds its own enable gate `STRIPE_RECONCILE_ENABLED === "true"` (default OFF, same pattern as retention) so scheduling it changes nothing until Noe switches it on. Unit-test the logic with mocked Stripe (missing events, mismatched statuses, a deauthorised club skipped and reported); integration-test the store writes under both roles.
4. Admin page `app/admin/stripe`: per club: connection (id, flag, cached status, refreshedAt), event counts by status (24 h / 7 d), last event, failed and received-but-unprocessed events with type, created, attempts, last error (truncated; no PII), a Replay button (step-up + reason), and the last reconcile run summary with mismatches. No secrets; no free-form editing. Follow `docs/UI-RULES.md`.
5. Proofs required: (a) duplicate delivery (same id twice, sequential and concurrent): one processing, one Payment row, one audit row; (b) out-of-order events: the store records both; the handler rule (lane PC) applies the newer — your DB test covers the store, PC's covers the rule; (c) crash mid-handler (throw after the Payment insert, before commit): no Payment row, row `failed` with the error, a retry processes once, exactly one Payment row at the end; (d) replay of a failed event after the cause is removed: processed once; (e) forced replay of a processed event: no duplicate financial effect; (f) reconcile finds a deliberately deleted store row and records it as missing without processing it.
