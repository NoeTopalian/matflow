Design to implement:
1. New model `MemberSubscription { id, tenantId, memberId, stripeAccountId, stripeSubscriptionId @unique, source ("app" | "migration" | "adopted"), status (Stripe status mirror), currentPeriodEnd?, lastEventCreated Int? (Stripe `event.created` of the last applied event), createdAt, endedAt?, @@index([tenantId, memberId]) }`. Backfill: a migration SQL step that inserts a row for every Member with a non-null `stripeSubscriptionId` (tenant's `stripeAccountId`, source "adopted"). `Member.stripeSubscriptionId` stays as a denormalised pointer to the member's ACTIVE mapping (set only from a mapping row, never from an arbitrary event).
2. Every in-app and migration create writes the mapping in the same transaction as the Stripe id and sets `metadata: { matflowTenantId, matflowMemberId, matflowSource }` on the Stripe subscription (migration already does; make app creates do the same).
3. Webhook resolution order: `event.account` → tenant (existing); then for subscription events resolve by `data.object.id` → `MemberSubscription` (tenant-scoped); for invoice events resolve by `invoice.subscription` → mapping, else by `invoice.metadata`/`checkout session metadata` for one-offs MatFlow created, else by the existing Payment row keyed on the invoice/PI id. If nothing maps the object to a MatFlow record, the event is **acknowledged and recorded as `ignored_foreign`** (lane PD's store will carry the status; until PD lands, log it and return 200) and nothing on any Member is written. Customer-only resolution is removed except for `customer.deleted` and `payment_method.detached` (which only clear links).
4. Ordering: before applying a subscription event, compare `event.created` with the mapping's `lastEventCreated`; an older event is recorded as `ignored_stale` and not applied. For invoices, keep the per-Payment terminal-state rule (`succeeded` is never overwritten by a later-delivered `failed` for the same invoice; a `failed` followed by `succeeded` is applied). Where state matters and the event may be stale, retrieve the object fresh from Stripe with `Stripe-Account` (docs recommend it) — do so for `customer.subscription.updated` when the event is older than the mapping or when the mapping has no `lastEventCreated`.
5. Separation of states: a subscription event updates the mapping's status and the member's `paymentStatus` (through the existing map) ONLY if the mapping is the member's ACTIVE one; it never sets `Member.status = "cancelled"`. `incomplete_expired` or `canceled` on a mapping that is NOT the member's active subscription (for example an abandoned signup while a desk tier or another mapping is live) ends that mapping and leaves the member untouched. `canceled` on the active mapping: end the mapping, null `Member.stripeSubscriptionId`, set `paymentStatus` per the existing map; `Member.status` is left to MatFlow (staff action) — record in the report where the old code cancelled the member and what now happens instead, so lane PB and the owner can decide the member-facing message. Also handle `invoice.payment_action_required` (add to handled events): record it on the Payment/mapping as `requires_action` without changing entitlement.
6. `livemode`: refuse (400, not claimed) any event whose `livemode` does not match the mode of `STRIPE_SECRET_KEY` (test key ↔ livemode false). Unit test both ways.
7. Tests required (unit, mocked Prisma per the existing pattern, plus DB integration with real rows under both roles): (a) simultaneous old (foreign, no mapping) and replacement (mapped) subscriptions on one customer: updates/cancellation of the foreign one change nothing on the member; (b) delayed `subscription.updated` (older `created`) after a newer one: ignored; (c) two mapped subscriptions for one payer (parent paying for two children: separate customers today, but also one customer with two mappings): each event touches only its own mapping/member; (d) late `invoice.payment_failed` after `payment_succeeded` for the same invoice: no overwrite; (e) `incomplete_expired` on a non-active mapping leaves `Member.status` and `paymentStatus` unchanged; on the active mapping clears the pointer only; (f) unknown subscription id on a known account → `ignored_foreign`, 200, no writes; (g) livemode mismatch → 400, no claim; (h) the existing dedup and transaction tests still pass.
