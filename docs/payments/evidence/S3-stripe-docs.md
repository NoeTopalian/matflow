## Q2 (provider side) - Standard accounts: OAuth vs Account Links vs Account Sessions; existing accounts

Sources (read 2026-10-11): https://docs.stripe.com/connect/standard-accounts ; https://docs.stripe.com/connect/oauth-standard-accounts ; https://docs.stripe.com/connect/oauth-reference ; https://docs.stripe.com/connect/oauth-changes-for-standard-platforms

2.1 Legacy status of the "Standard" type. The Standard-accounts page now carries a "Deprecated feature" box: "The information on this page applies only to platforms that already use legacy connected account types (Standard, Express, or Custom accounts). If you are setting up a new Connect platform, or your integration uses the Accounts v2 API, see the Interactive platform guide." It points new integrations to Accounts v2 or to Accounts v1 with controller properties. [standard-accounts, 2026-10-11]. Implication: "Standard" is a legacy label. It still works (the page documents it), but Stripe now describes the same thing as an account where the connected account has full Dashboard access, pays its own Stripe fees and carries its own losses (controller properties). See 2.6.

2.2 OAuth is not recommended for new platforms. Verbatim: "OAuth is not recommended for new Connect platforms. We recommend using Connect Onboarding for Standard accounts instead." [oauth-standard-accounts, 2026-10-11]. And: "The process described here [accounts.create type=standard + Account Links] is the recommended method for creating standard accounts. If you are an extension or an application that needs access to an existing account so you can provide services to your users, you can still use OAuth." [standard-accounts, 2026-10-11]. OAuth remains documented and functional (authorize, token, deauthorize endpoints in oauth-reference).

2.3 Platform-created Standard accounts are allowed. The platform may call `POST /v1/accounts` with `type=standard` (prefill optional), then `POST /v1/account_links` with `type=account_onboarding`, `refresh_url`, `return_url`, and redirect the user. Account Link URLs are single-use, expire after "a few minutes", must not be emailed or texted, and require the user to be authenticated in the platform first. `return_url` "does not mean that all information has been collected"; check `details_submitted` / `charges_enabled` via `account.updated` or a retrieve. Live mode requires HTTPS return/refresh URLs. After the first account link, the platform can no longer read or write KYC data on a Standard account. [standard-accounts, 2026-10-11]

2.4 Connecting an EXISTING Stripe account. Only OAuth is documented as the way for a user to connect an account they already own: "The process of creating a Stripe account is incorporated into our authorization flow. You do not need to worry about whether or not your users already have accounts"; "The user is logged in and can choose an account to connect to your platform directly." [oauth-standard-accounts, 2026-10-11]. `accounts.create` + Account Links always creates a NEW account (the create call returns a new account id) [standard-accounts, 2026-10-11]. So OAuth is the right documented route for a club that already has a Stripe account and wants to keep it.

2.5 IMPORTANT LIMIT - accounts controlled by another platform. "Platforms using OAuth with read_write scope cannot connect to Standard accounts that are controlled by another platform. Prior to June 2021, multiple platforms could connect to the same Standard account." ... "When a user of a Standard account controlled by another platform connects to your platform, the Connect onboarding flow directs them to create a separate Standard account to use with your platform. The new account automatically connects to your platform." Only Extensions may connect to accounts already connected elsewhere and only Extensions may use `read_only`. [oauth-changes-for-standard-platforms, 2026-10-11; oauth-reference, 2026-10-11]. Consequence for the owner plan: if a club existing Stripe account was CREATED by or is CONTROLLED by another platform (for example an account created through another gym software onboarding), MatFlow cannot attach to that same account; Stripe will steer the owner into a new, separate account, and the customers, saved cards and subscriptions in the old account will not be visible to MatFlow. Whether TeamUp-era accounts are "controlled by another platform" cannot be determined from docs - see UNKNOWN list. A self-created Stripe account that was merely OAuth-connected to another platform is not described as "controlled"; the docs do not spell out the exact test, so this needs confirmation on the real account.

2.5a What "controlled by another platform" means (Stripe Support, read 2026-10-11, https://support.stripe.com/questions/security-permissions-and-access-levels-when-connecting-your-stripe-account-to-a-third-party-platform): accounts "created during platform onboarding" are "automatically enabled with Platform Controls" and their users "cannot revoke access"; users "who registered directly with Stripe (not during platform onboarding)" can revoke access from Authorized Applications. So the test is how the gym's account was CREATED: an account the owner opened himself at stripe.com is not platform-controlled and OAuth can attach to it; an account that was opened inside another software's onboarding flow is controlled by that platform, and MatFlow's OAuth will push the owner into a new, empty account.

2.5b Testing note (https://docs.stripe.com/connect/testing, read 2026-10-11): the test `client_id` allows non-HTTPS and localhost redirect URIs and force-skipping the account form; "You can also test connecting an existing Stripe account only if the email is different from your platform account."

2.6 Account Sessions / embedded onboarding: the Standard page does not offer Account Sessions; Stripe current guidance routes new platforms to Accounts v2 / controller properties and embedded components (see 2.1). Not needed for the OAuth path in the repo. [standard-accounts, 2026-10-11]

2.7 OAuth mechanics relevant to the repo implementation [oauth-reference, 2026-10-11]:
- `state`: "An arbitrary string value we will pass back to you, useful for CSRF protection." Stripe does NOT sign, expire or bind `state`; the platform must ("Your site should confirm the state parameter has not been modified" [oauth-standard-accounts]).
- `code`: "can only be used once and expires in 5 minutes". The token endpoint "is not idempotent. Consuming an authorization code more than once revokes the account connection." So a retried or double-submitted callback can disconnect the club.
- Mode: the API key used at `/oauth/token` must match the mode of the `client_id` (live vs test); mismatches return `invalid_grant`. Response gives `stripe_user_id` (store it), `livemode`, `scope`; `access_token`, `stripe_publishable_key`, `refresh_token` are Deprecated - use the `Stripe-Account` header with the platform key.
- `scope`: `read_write` is required for a platform; `read_only` is Extensions-only.
- `redirect_uri` must exactly match one configured in OAuth settings; live mode requires HTTPS. OAuth onboarding must be enabled in Dashboard settings (Connect > Onboarding options > OAuth) and a separate test vs live `client_id` exists [oauth-standard-accounts].
- Data visibility warning: "data you create for a Standard account (charges, customers, invoices, and so on) will be visible on their Stripe account. This also means if they connect other platforms, those platforms will have access to that data too." [oauth-reference]

## Q3 - Platform requirements before LIVE connections; liability and the platform profile

Sources (read 2026-10-11): https://docs.stripe.com/connect/design-an-integration ; https://docs.stripe.com/connect/express-accounts ; https://docs.stripe.com/connect/accounts ; https://docs.stripe.com/connect/risk-management ; https://docs.stripe.com/connect/oauth-standard-accounts ; https://docs.stripe.com/connect/standard-accounts

3.1 Connect onboarding of the platform is a documented prerequisite. "Before starting your integration in a sandbox environment, you must create a Stripe Account or log in and onboard your platform to Connect" - the link target is `https://dashboard.stripe.com/settings/connect/platform-profile`. [design-an-integration, 2026-10-11]. The Express page lists "Platform profile: You need to complete your platform profile" as an explicit requirement for Express accounts. [express-accounts, 2026-10-11]. The Standard and OAuth pages do NOT list the platform profile as a requirement in words; they require Connect branding in Connect settings (name, colour, icon - "Connect Onboarding requires this information") for the Account Links route [standard-accounts], and for OAuth: enable OAuth in Connect > Onboarding options > OAuth, copy the live `client_id`, set an HTTPS live `redirect_uri` [oauth-standard-accounts; oauth-reference]. The Connected-account-types page says "To learn which account type we recommend for your business, refer to your platform profile" [accounts, 2026-10-11].
   Plain reading: Stripe docs treat "onboard your platform to Connect" (the platform-profile page) as the entry step for any Connect platform, sandbox or live. No docs page I read says a Standard/OAuth-only platform is exempt. Whether MatFlow live account has completed it is an owner/Dashboard fact, not answerable from docs.

3.2 What the owner declined vs what is mandatory. The responsibility screens the owner declined on 17 Sep (per the repo memory note `project_stripe_connect_liability_decision.md`: platform loss liability, and platform requirement-collection) correspond to the two "Platform is responsible" options documented in risk-management and design-an-integration. The docs show the alternative is legitimate and is the recommended SaaS default: "Stripe monitors risk signals on connected accounts ... and seeks to recover negative balances from your connected accounts. For most software as a service platforms, this is the best default choice" [design-an-integration, 2026-10-11]. With "Stripe is responsible": "Stripe covers losses due to your connected accounts negative balances", "Stripe is responsible for collecting KYC information", connected accounts "can use the full Stripe Dashboard", and the platform cannot pause payouts or debit connected accounts [risk-management, 2026-10-11]. Legacy Standard table: "Fraud and dispute liability: Connected account for direct charges, Platform for destination charges"; "Onboarding: Stripe"; "Identity information gathering: Stripe" [accounts, 2026-10-11].
   So declining PLATFORM responsibility is consistent with Standard + direct charges. It does not by itself mean the platform profile is complete; Stripe may still require the profile questionnaire (business model, fund flow, who is responsible = Stripe/connected account) to be submitted before live Connect use. Flag: needs the owner to look at `dashboard.stripe.com/settings/connect/platform-profile` in LIVE mode and record its state (see UNKNOWN list).

3.3 Live-mode specifics documented:
- Separate live vs test OAuth `client_id`; the live API key must match the live `client_id` at `/oauth/token` and at `/oauth/deauthorize` ("Use a live mode API key if a production client_id created the connection") [oauth-reference, 2026-10-11].
- Live `redirect_uri` must be HTTPS and must exactly match one configured in the live OAuth settings [oauth-reference, 2026-10-11].
- Account Link `return_url`/`refresh_url` must be HTTPS in live mode [standard-accounts, 2026-10-11].
- I found no docs statement of a Stripe manual review/approval step for Standard OAuth platforms. A third-party help page (Sharetribe, not Stripe, https://www.sharetribe.com/help/en/articles/9453619-troubleshoot-stripe-errors, surfaced by search 2026-10-11, not opened) claims Stripe reviews platform-profile submissions within hours; this is NOT official and is about a marketplace (Express/destination) setup. Treat as unverified.

3.4 Legacy-type warning for a new platform. Every legacy-type page I read (standard-accounts, accounts, express-accounts) now carries "Deprecated feature ... applies only to platforms that already use legacy connected account types" and points new platforms to Accounts v2 / controller properties [accounts, 2026-10-11]. "Stripe recommends that you use controller properties instead of account types" [accounts]. OAuth "is not recommended for new Connect platforms" [oauth-standard-accounts]. This does not stop OAuth working, but the owner plan assumes a mainstream, recommended path; the docs say it is a legacy path kept mainly for extensions and existing platforms. Risk: future changes land on the recommended path first. It is not a blocker for a first club.

## Charge types for Standard accounts (supports Q4 money trace; S2 owns the code side)

Sources (read 2026-10-11): https://docs.stripe.com/connect/accounts ; https://docs.stripe.com/connect/charges ; https://docs.stripe.com/connect/direct-charges.md?platform=web&ui=stripe-hosted ; https://docs.stripe.com/connect/direct-charges-fee-payer-behavior ; https://docs.stripe.com/connect/subscriptions

C.1 Standard supports direct charges only. Legacy comparison table: "Supported charge types: Direct only" for Standard [accounts]. "We recommend using direct charges for connected accounts that have access to the full Stripe Dashboard" [direct-charges]. "Direct charges are recommended for connected accounts with access to the full Stripe Dashboard, which includes Standard accounts" [subscriptions]. Requires the `card_payments` capability active on the connected account [charges].

C.2 Merchant of record. Direct charge: charge created on the connected account; "Merchant of record: Connected account"; customers "see its statement descriptor" [subscriptions table]. "The payment appears as a charge on the connected account, not your platform account"; Checkout uses the connected account branding [direct-charges].

C.3 Platform fee is optional. `application_fee_amount` (one-off) / `application_fee_percent` (subscriptions) are optional ("Optionally, you can specify a percentage...") [subscriptions; direct-charges]. No Stripe requirement forces a platform fee. A platform taking its fee by bank transfer outside Stripe is compatible with the docs: simply omit both parameters. (S2 must confirm the code passes neither.)

C.4 Stripe fees. Accounts created with `type=standard` have `controller.fees.payer = account`: "Stripe collects fees directly from your connected account. We do not charge any Connect fees to it or to your platform." Dispute fees, Billing (Invoicing and Subscriptions) fees, Radar, Stripe Tax: all "Connected Account" for payer `account` [direct-charges-fee-payer-behavior]. Note: "Any activity occurring at the platform account level is billed to your platform regardless" - so anything MatFlow creates WITHOUT the `Stripe-Account` header (platform-level customers, charges) would be billed to MatFlow and would make MatFlow the merchant [direct-charges-fee-payer-behavior; charges].

C.5 Refunds. Direct charges: "Stripe debits the refund amount from the connected account balance directly when you create a refund. If the connected account balance is insufficient, we set the refund status to pending" and process it later [charges]. Platform may create refunds on a connected account with its secret key and the `Stripe-Account` header [direct-charges]. Application fees are not auto-refunded (`refund_application_fee`) - irrelevant if no fee is taken.

C.6 Disputes. "For disputes on payments created using direct charges, Stripe debits the disputed amount from the connected account balance, not your platform balance." Dispute fee payer for legacy Standard: connected account [charges; direct-charges-fee-payer-behavior]. Ultimate unrecoverable negative balance: depends on loss responsibility (`controller.losses.payments`: `stripe` vs `application`) [risk-management]; Standard table gives "Fraud and dispute liability: Connected account for direct charges" [accounts]. The gym responds to disputes in its own Dashboard; the platform can see disputes via the API with `Stripe-Account`.

C.7 Payouts. Direct-charge funds settle into the connected account balance and pay out on the connected account schedule; a platform without platform controls cannot set payout timing (platform controls exist only on platform-controlled accounts) [charges; platform-controls-for-stripe-dashboard-accounts, 2026-10-11].

## Q8 (provider side) - What MatFlow can access on a Standard account via `Stripe-Account`

Sources (read 2026-10-11): https://docs.stripe.com/connect/authentication ; https://docs.stripe.com/connect/subscriptions ; https://docs.stripe.com/connect/oauth-reference ; https://support.stripe.com/questions/security-permissions-and-access-levels-when-connecting-your-stripe-account-to-a-third-party-platform ; https://docs.stripe.com/connect/platform-controls-for-stripe-dashboard-accounts ; https://docs.stripe.com/connect/direct-charges.md?platform=web&ui=stripe-hosted

8.1 Mechanism. Server-side calls use the platform secret key plus `Stripe-Account: acct_...`; client-side Stripe.js takes `stripeAccount` [authentication]. OAuth `access_token` is deprecated in favour of this header [oauth-reference]. Direct-charge objects (PaymentIntents, Charges) "exist on the connected account, not on the platform" and must be queried with the header [direct-charges].

8.2 Scope of access with `read_write` (Stripe Support, official but help-centre, read 2026-10-11): platforms can "Create and update any object: customers, charges, invoices, plans, coupons, and subscriptions", "Refund any charge", "Delete customers", plus read access; they "cannot view credit card numbers or copy them off of Stripe" [support article]. So listing and reading customers, subscriptions and invoices that the gym created itself (Dashboard) is within read_write, as worded.

8.3 Documented limits on objects made by OTHER platforms [subscriptions, 2026-10-11]:
- "Your platform cannot update or cancel a subscription that another platform created."
- "Your platform cannot add an application_fee_amount to an invoice that it did not create, nor to an invoice that contains invoice items the platform did not create."
- "Only connected accounts with access to the full Stripe Dashboard can manage their customers subscriptions. For other connected accounts, the platform must manage their customers subscriptions."
   Implication for TeamUp coexistence: if Sean subscriptions were created by TeamUp acting as a Connect platform on HIS account, MatFlow cannot cancel or modify them through the API; Sean (or TeamUp) must cancel them in his Dashboard or in TeamUp. If TeamUp subscriptions live in TeamUp own Stripe account (not Sean), MatFlow cannot see them at all. Docs do not say whether a subscription created by the account owner in the Dashboard counts as "another platform"; by wording it does not, but this is untested (UNKNOWN list).

8.4 Shared visibility. "Data you create for a Standard account (charges, customers, invoices, and so on) will be visible on their Stripe account. This also means if they connect other platforms, those platforms will have access to that data too." [oauth-reference]. MatFlow-created data is therefore not private to MatFlow; the gym (and any other connected platform or extension) can alter it, which is why webhook-driven sync is required rather than assuming MatFlow is the only writer.

8.5 Payment methods. Customers and payment methods must exist on the connected account for direct-charge subscriptions ("define the customer with a default payment method and the Price on the connected account") [subscriptions]. Card numbers cannot be exported by a platform [support article]. Payment methods saved on a DIFFERENT Stripe account (for example TeamUp own account) are not reachable through the `Stripe-Account` header; moving them needs Stripe data migration (not researched further here - see UNKNOWN).

## Q12 (provider side) - Webhooks for connected accounts

Sources (read 2026-10-11): https://docs.stripe.com/connect/webhooks ; https://docs.stripe.com/webhooks ; https://docs.stripe.com/events/manage-webhook-endpoints ; https://docs.stripe.com/connect/subscriptions

12.1 Two scopes, two endpoints. "Your account" scope = events for objects on the platform account (requests made without `Stripe-Account`). "Connected accounts" scope = events for objects that live on connected accounts, including "Direct charges for customers of your connected accounts", `account.updated`, and disconnections. Dashboard: "Events from: Your account / Connected accounts"; API: `connect=true` on the v1 webhook endpoint, or `events_from=["@accounts"]` on v2 event destinations [connect/webhooks; webhooks]. For a Standard + direct-charge integration, every member payment, invoice, subscription and dispute event lives on the connected account and arrives ONLY at a Connected-accounts endpoint.

12.2 Signing secrets. "Stripe generates a unique secret key for each endpoint. If you use the same endpoint for both test and live API keys, the secret is different for each one. Additionally, if you use multiple endpoints, you must obtain a secret for each one you want to verify signatures on." [webhooks, 2026-10-11]. So a platform that registers both a "Your account" endpoint and a "Connected accounts" endpoint has two different `whsec_` values even if both point at the same URL. Repo comparison: `app/api/stripe/webhook/route.ts:33` reads a single `STRIPE_WEBHOOK_SECRET` and verifies with `stripe.webhooks.constructEvent(rawBody, sig, webhookSecret)` (line 43) using the raw body from `req.text()` (line 31). That is correct only if exactly ONE endpoint (the Connected-accounts one) is registered at that URL in each mode; a second endpoint at the same URL would fail verification (400) for all its events. Which endpoints exist in the live Dashboard is UNKNOWN.

12.3 `account` field. "Each event for a connected account contains a top-level `account` property that identifies the connected account. Because the connected account owns the object that triggered the event, you must make API requests for that object as the connected account." [connect/webhooks]. The repo reads `event.account` at `route.ts:59` (S1 owns the tenant-binding check).

12.4 Livemode. "For Connect webhooks, your development webhook URLs receive only test webhooks, but your production webhook URLs receive both live and test webhooks. This is because you can perform both live and test transactions under a production application. We recommend that you check the `livemode` value when receiving an event webhook." [connect/webhooks, 2026-10-11]. Repo comparison: grep of `app/api/stripe/webhook/route.ts` finds no `livemode` reference. Consequence per docs: a club testing in test mode against the production MatFlow Connect application can deliver test-mode events to the production endpoint; unless the signature differs (test events to a live endpoint are signed with the endpoint secret for that mode - the docs say the secret differs per mode for the same endpoint, so a live-secret verifier would reject test-mode deliveries signed with the test secret) - the docs do not state which secret signs a test event delivered to a production Connect URL. Treat as UNKNOWN and add an explicit `livemode` check rather than relying on secret separation.

12.5 Delivery semantics the handler must tolerate [webhooks; manage-webhook-endpoints, 2026-10-11]:
- Retries: "Stripe attempts to deliver events to your destination for up to three days with an exponential back off in live mode"; sandbox: "three times over the course of a few hours". Any non-2xx (including 409 and 3xx) is a failure and is retried.
- Manual resend: Dashboard up to 15 days; CLI up to 30 days. List Events API "only returns events created in the last 30 days"; `delivery_success=false` filter exists for backlog recovery.
- Ordering: "Stripe does not guarantee the delivery of events in the order that they are generated ... Do not use `created` to determine event order ... Track event IDs to identify duplicate deliveries"; retrieve missing objects via the API.
- Duplicates: "Webhook endpoints might occasionally receive the same event more than once" - log processed event IDs; "In some cases, two separate Event objects are generated" - dedupe also by `data.object.id` + `event.type`.
- Respond fast: "return a successful status code (2xx) before any complex logic that could cause a timeout"; process asynchronously via a queue for month-start spikes.
- Replay: library default tolerance 5 minutes; do not set 0.
- Event-generation failures (public preview): Stripe can fail to create an Event at all; recovery is polling the object [manage-webhook-endpoints]. So webhooks alone cannot be the only sync path - a reconcile job is the documented fallback.
- Payload version: "The API version in your account settings when the event occurs dictates the API version, and therefore the structure of an Event sent to your destination" unless the destination has its own API version [webhooks]. See Q-API below.
- Secret rolling: up to 24h overlap with two signatures [webhooks].

12.6 Listing missed connected-account events. The List Events example uses the platform key alone; for events whose objects live on a connected account, docs say API requests for those objects must be made "as the connected account" [connect/webhooks]. Inference (not stated verbatim): backlog recovery for Standard accounts must list events per connected account with `Stripe-Account`. Needs confirmation in test mode.

## Q18 (provider side) - Deauthorisation, disconnection and outages

Sources (read 2026-10-11): https://docs.stripe.com/connect/oauth-reference ; https://docs.stripe.com/connect/oauth-standard-accounts ; https://docs.stripe.com/connect/webhooks ; https://docs.stripe.com/connect/subscriptions ; https://docs.stripe.com/connect/platform-controls-for-stripe-dashboard-accounts ; https://support.stripe.com/questions/security-permissions-and-access-levels-when-connecting-your-stripe-account-to-a-third-party-platform ; https://docs.stripe.com/error-low-level

18.1 Who can disconnect. Gym side: users "who registered directly with Stripe (not during platform onboarding) can revoke platform access anytime via the Authorized Applications page in their dashboard"; accounts created during platform onboarding are platform-controlled and "cannot revoke access" [support article, 2026-10-11]. Platform side: `POST https://connect.stripe.com/oauth/deauthorize` with `client_id` + `stripe_user_id`, using a key of the same mode as the connection; "You can only revoke a Standard account's access to your platform"; or Dashboard "Remove account" [oauth-reference]. Error `no_deauth_on_controlled_account` exists for controlled accounts (use the reject API instead) [oauth-reference].

18.2 Effect on access. "After revocation, the account can't be accessed by your platform in the Dashboard or through the API. The account can continue to access its own data and functionality through the account's Dashboard." [oauth-reference]. Removing the account "permanently resets all platform controls on the account ... even if the account reconnects later. It doesn't otherwise affect the account, which still functions as a normal Stripe account." [platform-controls-for-stripe-dashboard-accounts].

18.3 The event. `account.application.deauthorized` - data.object type `application`; "Occurs when a connected account disconnects from your platform ... Available for connected accounts with access to the Stripe Dashboard, which includes Standard accounts." It is a Connected-accounts-scope event with top-level `account` [connect/webhooks; connect/subscriptions]. Because API access is gone at that point, the handler can only update local state; it cannot call the connected account to cancel anything.

18.4 What survives a disconnect (direct charges). "When a connected account is disconnected from a platform, subscriptions aren't automatically canceled." For direct charges: "After disconnect, subscriptions continue to run on the connected account. If the subscription was created with an application_fee_percent, the application fee continues to be collected by the platform after disconnect." [connect/subscriptions, 2026-10-11]. Plain consequence for MatFlow: after a gym disconnects, its members keep being billed by the GYM's Stripe account on the existing schedule, MatFlow stops receiving events for them and can no longer cancel, pause or refund them. Any MatFlow-side pause, hold, cancel-on-member-delete or refund feature silently stops working for that club. Owner decision needed on what MatFlow shows (for example, mark billing as unmanaged); the docs give no automatic clean-up.

18.5 Reconnection. Docs do not describe a special reconnect path; the gym repeats OAuth. Previously created customers/subscriptions remain on the gym's account and should become reachable again once reconnected (they never left the account) - inference from 18.2, not stated verbatim for the reconnect case. Platform controls do not come back [platform-controls-for-stripe-dashboard-accounts].

18.6 Stripe outage / indeterminate results. "Treat the outcome of a request that returns 500 as indeterminate: the operation might have produced side effects ... Don't retry with a new idempotency key until you've resolved the original outcome." "During incident recovery, Stripe attempts to reconcile failed operations and send webhook events for any objects created during reconciliation ... reconciliation isn't guaranteed to resolve every operation." "When creating a resource, include a local identifier in its metadata so you can match an object received through a webhook to your local records." [error-low-level, 2026-10-11]. Network timeouts: "Restoring connectivity doesn't tell you whether the original request succeeded" - retry with the SAME key and parameters within 24 hours, then stop and reconcile [error-low-level].

## Idempotency keys and retries (supports Q13)

Sources (read 2026-10-11): https://docs.stripe.com/api/idempotent_requests ; https://docs.stripe.com/error-low-level ; local SDK source `node_modules/stripe/cjs/RequestSender.js:198-212`, `node_modules/stripe/cjs/stripe.core.js:158`

I.1 Semantics (API v1). "Stripe saves the status code and body of the first request made with a given idempotency key after endpoint execution begins. Retries with the same key return the saved response, including 500 errors." Keys up to 255 characters; "Avoid using sensitive data (for example, email addresses or personal identifiers) as idempotency keys". Keys can be pruned after at least 24 hours; reuse after pruning executes a NEW request. Parameter mismatch with the same key errors. Validation failures and concurrent-conflict results are NOT saved and may be retried. Keys apply to POST only; GET/DELETE ignore them [idempotent_requests, 2026-10-11].

I.2 Retry rules. Same key + same params within 24 h for network errors; on 409 "another request with the same key is still executing, wait and retry with that key"; "A new key can start a second operation"; after 24 h with unknown outcome, reconcile (retrieve object, Dashboard, webhooks) or contact Stripe before repeating [error-low-level]. Honour `Stripe-Should-Retry` (SDKs do automatically).

I.3 SDK behaviour (local source, stripe 22.0.1): default `maxNetworkRetries` is 2 (`stripe.core.js:158`); for v1 POSTs with retries > 0 the SDK auto-generates `stripe-node-retry-<uuid4>` when the caller supplies none (`RequestSender.js:198-212`). That automatic key covers only the retries inside ONE SDK call. Docs: "If your application retries across separate SDK calls or process restarts, generate and persist a key for the operation and supply it to every attempt" [error-low-level]. So a double-click or a re-entered route gets a fresh random key and can create a duplicate object unless the route supplies its own deterministic key. Repo examples that do supply deterministic keys (S1 owns the full list): `app/api/members/[id]/charge/route.ts:165` (`matflow_adhoc_${memberId}_${requestId}`), `app/api/payments/[id]/refund/route.ts:190`, `lib/stripe/subscriptions.ts:151`, `lib/stripe/migrate-memberships.ts:671`. Note: the refund key embeds the amount and the locally-recorded refunded total; it contains no personal data (allowed), but it changes whenever local state changes, so a retry after a partial local write would produce a different key - S1 to assess.

I.4 OAuth token exchange is NOT idempotent: "Per OAuth v2, this endpoint isn't idempotent. Consuming an authorization code more than once revokes the account connection." [oauth-reference]. Idempotency keys do not protect `/oauth/token`; the callback must make code consumption single-shot.

## API version handling in the SDK

Sources (read 2026-10-11): https://docs.stripe.com/sdks/set-version ; https://docs.stripe.com/upgrades ; https://docs.stripe.com/webhooks/versioning ; https://docs.stripe.com/webhooks ; local `node_modules/stripe/cjs/apiVersion.js:5`, `node_modules/stripe/cjs/stripe.core.js:97,156`

V.1 stripe-node v12+ pins requests to the API version current at SDK release; `apiVersion` overrides it globally or per request; "The TypeScript types reflect the latest API version at the time of release" [set-version]. Locally, 22.0.1 defaults to `2026-03-25.dahlia` (`apiVersion.js:5`, `stripe.core.js:97,156`) and the app also passes it explicitly, so code version = SDK types version. Consistent.

V.2 Latest version on 2026-10-11: the docs examples use `2026-09-30.endive` [set-version; upgrades]. Release model since 2024-09-30.acacia: monthly releases with no breaking changes; "Twice a year, we issue a new major release ... that starts with an API version containing breaking changes" [webhooks/versioning]. MatFlow is therefore one major release behind (dahlia, March 2026; endive, September 2026). Not a defect; upgrading is a deliberate project.

V.3 Webhook payload version is independent of the SDK. "Each webhook endpoint has a specific API version. Stripe uses that version to structure the event payloads it sends to the endpoint" [webhooks/versioning]; "The API version in your account settings when the event occurs dictates the API version" unless the destination sets its own; for v2 event destinations `snapshot_api_version` "is independent of the API version used by your server-side SDK" and can be set only at creation [webhooks; upgrades]. Risk: if the live Connected-accounts endpoint was created with (or defaults to) a version other than `2026-03-25.dahlia`, `data.object` shapes may differ from the dahlia types the handler assumes (the handler comment at `app/api/stripe/webhook/route.ts:77` relies on the dahlia Invoice shape). The live endpoint's version is UNKNOWN - an owner Dashboard check.

V.4 Upgrade method: create a second disabled endpoint with the new `api_version` and a distinguishing query parameter, dual-run, switch processing, then disable the old one; "your event handler must be idempotent because Stripe delivers subscribed events to both destinations" [webhooks/versioning; upgrades]. Thin events are unversioned and avoid this, but are a larger change.

V.5 Unverified: a search snippet (docs.stripe.com/api/connected-accounts, 2026-10-11) suggested that requests on behalf of connected accounts without a version use the platform's version; the fetched page does not contain that sentence. Not relied on; the app pins the version explicitly, so it does not affect API calls.

## Where the docs contradict or qualify what the owner's plan assumes

P.1 "Club owners connect their OWN existing Stripe accounts." Qualified. Works by OAuth only if the account was opened directly at Stripe. If it was opened through another platform's onboarding (possibly TeamUp's, if TeamUp is a Connect platform for Sean), Stripe will make the owner create a NEW separate account for MatFlow; customers, saved cards and subscriptions stay in the old account, out of MatFlow's reach [oauth-changes-for-standard-platforms; support article; 2.5, 2.5a].

P.2 "Standard Connect via OAuth is the standard path." Qualified. Stripe now labels Standard/Express/Custom as legacy ("Deprecated feature") and says "OAuth isn't recommended for new Connect platforms"; recommended routes are Accounts v2 or v1 with controller properties, and `accounts.create` + Account Links for new accounts [accounts; oauth-standard-accounts; standard-accounts]. It still works; it is not the path Stripe invests in.

P.3 "Platform-profile screens were declined, so Connect is set up without them." Unresolved by docs. Declining PLATFORM loss liability and PLATFORM requirement collection matches Standard/direct charges, and Stripe calls "Stripe is responsible" the best default for SaaS [design-an-integration; risk-management]. But the docs also say a platform must "onboard your platform to Connect" at the platform-profile page before integrating, even in a sandbox [design-an-integration]. Whether the live platform profile is complete (with Stripe/connected-account responsibility selected) is a Dashboard fact - see UNKNOWN U1.

P.4 "The platform fee is paid by bank transfer, not through Stripe." Consistent with the docs: application fees are optional on direct charges and subscriptions [direct-charges; subscriptions]. Standard accounts pay their own Stripe fees, dispute fees and Billing fees (`controller.fees.payer = account`) [direct-charges-fee-payer-behavior]. Caveat: anything created WITHOUT `Stripe-Account` is platform-level and billed to MatFlow with MatFlow as merchant [direct-charges-fee-payer-behavior; charges].

P.5 "Gyms carry their own losses." Consistent for direct charges on Standard: refunds and disputes debit the connected account; dispute fees fall on the connected account [charges; direct-charges-fee-payer-behavior; accounts]. Ultimate unrecoverable negative balance follows `controller.losses.payments` (`stripe` vs `application`) [risk-management].

P.6 "MatFlow can manage and migrate the club's existing memberships." Qualified. "Your platform can't update or cancel a subscription that another platform created" [subscriptions]. Subscriptions created by TeamUp as a platform on the gym's account cannot be cancelled by MatFlow's API; the gym (or TeamUp) must end them. Payment methods held on a different Stripe account (TeamUp's own) are not reachable via `Stripe-Account`.

P.7 "Disconnect ends billing through MatFlow." Incorrect if assumed. After disconnect, direct-charge subscriptions keep running on the gym's account; MatFlow loses API and event access and must not expect a clean-up call to succeed [subscriptions; oauth-reference].

P.8 "One webhook secret is enough." Only if exactly one endpoint exists at that URL per mode. Each endpoint (and each mode) has its own secret; production Connect endpoints receive both live and test events, so a `livemode` check is recommended [webhooks; connect/webhooks]. The repo uses one `STRIPE_WEBHOOK_SECRET` and has no `livemode` check (`app/api/stripe/webhook/route.ts:33`, grep 2026-10-11).
